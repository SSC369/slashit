## 1. What works when this lands

`/remember My preferred airline is Qatar Airways` finds "Preferred airline is
Emirates" among the ten nearest memories, saves nothing, and asks "Which is
correct?" with the new fact beside the old one. "Keep the new one" saves the new
fact and forgets the old through slice 2. "Keep the old one" discards the new
fact. "Both are correct" saves it and keeps both. "Decide later" leaves the
question waiting, with nothing saved. Edits are never checked. The conflict eval
set scores the check against NFR-7 on the real model.

This is the last slice. With it, FR-10 holds and all three slices can ship.

## 5. Internal contracts

```python
# memories/services/memory_service.py
SaveOutcome = MemorySavedDTO | MemoryConflictDTO | MemoryTooLongDTO | ModelRefused

@dataclass(frozen=True)
class MemoryConflictDTO:
    text: str                          # the new fact, not yet saved
    category: MemoryCategory | None    # decided now, used on save
    conflicting: list[MemoryDTO]       # live, in the model's order

async def save_resolved(*, user_id, text, category, original_input) -> MemoryDTO
async def resolve_conflict(*, user_id, text, category, original_input,
                           conflicting_ids: list[UUID], answer: ConflictAnswer
                           ) -> MemorySavedDTO | MemoryDiscardedDTO
```

`save_memory` gains one step between the embed and the judgement: the ten
nearest live memories with a vector. The adapter already drops any returned id
it did not offer.

`resolve_conflict` never calls the model, so an answer works while the model is
down:

| Answer | Memories does | Result |
|---|---|---|
| `KEEP_NEW` | `save_resolved`, then slice 2's `forget_memories` on the ids still live | `MemorySavedDTO` |
| `BOTH` | `save_resolved` | `MemorySavedDTO` |
| `KEEP_OLD` | nothing | `MemoryDiscardedDTO` |

`save_resolved` writes the memory with a NULL vector and queues slice 1's
`memories.reembed` job, per Q1. Until the job runs, the memory is not a
candidate.

**The scrub reaches the thread (FR-23).** The question turn holds the typed
`/remember <fact>` but no memory id; the resolution turn carries both the
pending id and the new memory's id. The scrub also blanks every turn sharing a
`resulting_pending_capture_id` with a turn it scrubs. No row gains an id after
it is written, so AD-3's one `UPDATE` stays the only one.

**The index's rule holds.** A conflict turn's `question_text` is the fixed
"Which is correct?". Old memories are shown from live rows by id and never
copied into `capture_turns` or `pending_captures`.

```graphql
type MemoryConflictAsked {
  pendingCaptureId: ID!  question: String!  newText: String!
  category: MemoryCategory  conflicting: [Memory!]!
}
type MemoryDiscarded { message: String! }
enum ConflictAnswer { KEEP_NEW KEEP_OLD BOTH }
resolveMemoryConflict(pendingCaptureId: ID!, answer: ConflictAnswer!):
  MemorySaved | MemoryDiscarded | PendingCaptureNotFound
```

## 6. Error handling

| Case | Result | Where drawn |
|---|---|---|
| Model down during the save | Refused, text kept, as slice 1 (FR-9) | `CaptureStates` |
| An old memory is forgotten elsewhere before the answer | It drops out of the card and out of `KEEP_NEW`'s forget | `Main` |
| Every old memory is forgotten before the answer | `KEEP_NEW` and `BOTH` save plainly; `KEEP_OLD` still discards | `Main` |
| An old memory is edited before the answer | The card shows the new text: it reads live rows | `Main` |
| The pending row is already resolved or discarded | `PendingCaptureNotFound`; the card says it was answered elsewhere | 001's copy |
| The request fails | The card stays with 001's inline error; nothing changed | `Main` |
| The model returns an id it was not shown | Dropped by the adapter (slice 1) | none |
