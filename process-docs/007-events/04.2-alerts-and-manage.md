## 1. What works when this lands

Every lead in an `/add-event` line becomes an alert, and each fires as a
reminder notification that opens the event. A lead named twice is kept once.
A passed lead, or one over the 100-reminder cap, is named in the confirmation
and the rest are set. Yearly events re-arm every alert each year. Events can be
edited, with an alert list, and deleted with confirmation. Events are found by
`/search` and Records search, cite in answers, and show related records. A
timezone change moves each event and its alerts by FR-12 and FR-13. Slice 1's
"which alert?" question is gone.

## 5. Internal contracts

```python
# events/services/schedule.py, pure
def normalise_leads(*, leads: Sequence[int]) -> tuple[int, ...]: ...
    # distinct, ascending, each 0..MAX_ALERT_LEAD_MINUTES; reports whether any repeated
def alert_fire_times(*, resolved: Resolved, all_day: bool, leads: Sequence[int],
                     default_time: time, timezone: str) -> list[tuple[int, datetime]]: ...

# events/interfaces/ports.py
class EventAlertsPort(Protocol):
    async def set_alerts(self, *, user_id: UUID, event_id: UUID, title: str,
                         fire_times: Sequence[datetime], now: datetime) -> list[AlertNotSet]: ...
    async def clear_alerts(self, *, user_id: UUID, event_id: UUID) -> None: ...
```

`set_event_alerts` sorts the fire times, drops past ones as `passed`, counts
the user's active reminders without this event's own rows, inserts soonest
first until 100, and returns the rest as `cap`. It soft-deletes the event's
existing alert rows in the same transaction. Alert rows are one-time
reminders: `description` the event title, `origin` `command` or `edit` as the
event's change.

Order of writes, per Q1: create and edit write the event, then set its
alerts; delete clears the alerts, then deletes the event. A text-only edit
does not call `set_event_alerts`.

`updateEvent` takes the whole `EventInput`, as the form sends every field.
`EventInvalid` carries a field and a reason: `title`, `end_before_start`,
`limit` for an edit that would make a 501st upcoming event (FR-31).

## 6. Error handling

| Failure | Behaviour |
|---|---|
| Event saved, then setting alerts fails | Capture shows the event saved with its alerts not set, reason unknown. The 15-minute roll sweep finds the mismatch and re-sets them (Q1). Logged |
| Delete: alerts cleared, then the event delete fails | Event stays with no alerts; the sweep re-sets them; the dialog shows `DeleteEventFailed` |
| A lead already passed at capture or edit | Not set, named, reason `passed` (FR-19). The form disables Save for a passed row; the server still checks |
| Over the cap | Soonest first are set, the rest named, reason `cap` (FR-33) |
| Done or Snooze on an alert whose row an edit replaced | `ReminderNotFound`, drawn as 003 draws a deleted reminder |
| A pending `event_alert_choice` question from before deploy | Its answer saves the event with every lead, ignoring the chip |
| Yearly roll finds a lead longer than the time to next year's event | That alert is not set; counted in the job's log |
| Timezone change | All-day and yearly keep local fields; one-time timed keeps its instant; alerts re-set. Reminders' own rezone skips `event_id` rows |
| Embed fails | Three retries, then NULL for the backfill; words still match |
| Foreign or deleted id on update or delete | `EventNotFound` (dev log D-11) |
