## 1. What works when this lands

`/add-event` saves an event with every date rule applied and echoed back. A
missing date or two alert leads asks one question. The 501st upcoming event is
refused. `/events` lists upcoming events grouped by month. Records has an Events
tab, events appear under All, and detail shows every field. Every state drawn on
the Capture and Records pages exists, except edit, delete and the alert toast.

## 5. Internal contracts

```python
EVENT_EXTRACTION_SCHEMA = {
  "title": str, "start_date": "YYYY-MM-DD" | None, "has_year": bool,
  "start_time": "HH:MM" | None, "end_date": "YYYY-MM-DD" | None, "end_time": "HH:MM" | None,
  "location": str | None, "description": str | None,
  "repeat_yearly": bool, "alert_leads_minutes": list[int],
}
```

`has_year` lets FR-4 and FR-5 differ in code: no year and passed means next
year; a stated past year is kept. The instruction says "birthday" and
"anniversary" set `repeat_yearly` (FR-9). Descriptions stay terse, per capture's
measured latency note.

The confirmation's dim notes (design §8) come from `normalise_capture`, which
returns the rule it applied: `all_day`, `next_year`, `past_kept`, `overnight`,
`feb29`, `yearly_from_title`. Capture turns them into copy; no copy in events.

## 6. Error handling

| Failure | Behaviour |
|---|---|
| Model unavailable | Not-saved card, command kept, nothing written |
| No date | `pending_captures` row with `missing_field = event_date` and `candidate_event`; the answer is extracted as a date only |
| Two or more leads | `missing_field = event_alert_choice`; the chips are the leads plus "No alert"; nothing written until answered |
| Cap reached | `EventLimitReached` before insert, inside the transaction, counted with `FOR UPDATE` on the user's rows to avoid a race |
| Title over 200 or location over 200 | Truncated at a word boundary with "…", logged by length only |
| Detail for a missing or foreign id | `event` returns `null`; drawn not-found state |
