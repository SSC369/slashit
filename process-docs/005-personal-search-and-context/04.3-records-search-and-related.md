## 1. What works when this lands

Typing "career" in the records view lists the same nine records `/search
career` finds, best match first across all types, with the footer "9 records
match “career” · best match first". The type tabs narrow it; a tab with no
match says how many other records match. "Sorted by best match" switches to
date order. Every record's detail shows up to five records close in meaning
under Related, or "Nothing related yet", and a failed list never blocks the
detail. With slices 1 and 2, every must requirement in the PRD is met.

## 5. Contracts inside this slice

```python
# search/interfaces/dtos.py
@dataclass(frozen=True)
class SearchPageDTO:
    query: str
    hits: list[SearchHitDTO]        # citation always None here: never an answer
    total: int                      # matches in the chosen type, or all types
    other_types_total: int          # matches outside the chosen type; 0 with no type
    meaning_unavailable: bool

@dataclass(frozen=True)
class RelatedRecordDTO:
    record_type: RecordType
    item: RecordDTO

# search/services/search_service.py
async def search_page(
    self, *, user_id: UUID, text: str, record_type: RecordType | None, offset: int, limit: int,
) -> SearchPageDTO: ...
async def related(
    self, *, user_id: UUID, record_type: RecordType, record_id: UUID,
) -> list[RelatedRecordDTO]: ...
```

`search_page` runs slice 1's embed-while-word-pass and the combined pass, each
port asked for `offset + limit` candidates. It ranks by `rank_key`, filters to
the type, and slices `[offset : offset + limit]`. Totals are the ports' own.

`related` reads `embedding_of` from the record's port. No vector, or a record
the user does not own, gives an empty list. Otherwise every port runs with no
terms, that vector and `RELATED_MAX_DISTANCE`, limit six; the source record is
dropped, the rest sorted by distance, five kept.

```graphql
type SearchPage { query: String! hits: [SearchRecord!]! total: Int!
                  otherTypesTotal: Int! meaningUnavailable: Boolean! }
union SearchPageResult = SearchPage | SearchTooLong
extend type Query {
  search(text: String!, recordType: RecordType, offset: Int! = 0, limit: Int! = 50): SearchPageResult!
  relatedRecords(recordType: RecordType!, id: ID!): [SearchRecord!]!
}
```

| Rule | Value |
|---|---|
| `text` | 1 to 500 characters after trimming; longer is `SearchTooLong`, empty is a GraphQL error |
| `offset` | 0 or more |
| `limit` | 1 to 50 |

Frontend store, search mode:

| Field | Meaning |
|---|---|
| `searchRefs` | Ranked `{kind, id}` in server order, pages appended |
| `sortMode` | `BEST_MATCH` or `DATE`. `DATE` orders the loaded refs by created date, newest first |
| `searchQueryKey` | `text|type` of the page held. A response for another key is dropped |

> Assumption: "date" means created date, newest first, which every record type
> has. 001's FR-17 names created and due date; due date exists on tasks only.

> Assumption: a records view search records no `search_run`. It runs as the
> user types, so it would count keystrokes, not searches. Opening a row records
> `search_result_opened` with the row's position.

## 6. Error handling

| Failure | Result |
|---|---|
| Query embed fails or times out | `meaningUnavailable: true`, word matches listed, the amber strip (FR-20) |
| `search` fails outright | "Search could not run. Nothing is lost." with Try again; the box keeps its text |
| Session ended | 001's session-ended handling; "Sign in to search your records." |
| Offline | The drawn offline note; records already loaded stay readable |
| `relatedRecords` fails | "Related records could not be loaded." with Try again; the detail unaffected (FR-28) |
| A related record deleted since listed | Opening it shows 001's not-found page; the next open drops it |
| Another user's record id | `relatedRecords` returns an empty list; nothing leaks (T7) |
