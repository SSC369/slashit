## 1. What works when this lands

A person creates an account with a username, email and password; verifies it
with a code; and signs in. Their username shows in the app shell. 001's
dev-only console workaround is deleted, and every route except the five auth
screens requires a real session.

## 6. Error handling

| Failure | Detected by | User sees | System does |
|---|---|---|---|
| Email already registered | `signUp` error code | `02-design.md` Sign up, error state | Nothing written |
| Username taken | `handle_new_user()` trigger, unique violation, surfaced as a `signUp` error | Same error state, username field | Signup rolls back; Supabase does not leave a partial `auth.users` row on a failed trigger |
| Wrong password | `signIn` mutation returns `InvalidCredentials` | Sign in, error state, generic per FR-11 | `SignInInteractor` increments `auth_attempts` via `SqlAuthAttemptRepository` |
| Account locked (FR-17) | `signIn` mutation returns `AccountLocked` | Sign in, the "Too many attempts" card | No password check result is trusted either way; a locked account never reaches Supabase at all |
| Unverified account, sign-in (FR-10) | `signIn` mutation returns `AccountNotVerified` | Sign in redirects to Verify email | Not counted as a failed attempt: it is not a password check |
| Supabase unreachable during sign-in | `signIn` mutation returns `AuthProviderUnavailable` | Sign in, "temporarily unavailable" card | Not counted as a failed attempt |
| Too many signups (FR-19) | `hook_before_user_created` rejects | Sign up, the "Too many attempts" card | No `auth.users` row created |
| Wrong or expired code | `verifyOtp` error code | Verify email, wrong/expired states | Nothing written beyond Supabase's own attempt counting |
| Network failure, any call | Thrown/rejected promise | A generic retry-safe error, not one of the specific states above | No optimistic state changes anywhere in this slice |
